# Knowledge Base

Foundational facts about the project. Start here for orientation; go to `docs/ARCHITECTURE.md` for the how, `docs/REPOSITORY_MAP.md` for the where.

## What this project is
- **Project:** Kotak Bank / **Kotak811** website migration to **AEM Edge Delivery Services (EDS)**.
- **Repository:** `xeragobiz/kotakbank` (GitHub).
- **Starter:** `aem-boilerplate-xwalk` (Universal Editor / "crosswalk" / xwalk project).
- **Content source:** AEMaaCS author `author-p165370-e1760075.adobeaemcloud.com`, delivered via `bin/franklin.delivery/xeragobiz/kotakbank/main` (declared in `fstab.yaml`), authored in **Universal Editor**.
- **Goal:** Reproduce Kotak811 marketing pages faithfully — including animations — with dedicated, purpose-built `k811-*` blocks and a scoped design guide, not by force-fitting shared boilerplate blocks.

## The stack (and what it is NOT)
- **Is:** vanilla JavaScript ES6+ modules, CSS3 (optional block SCSS compiled locally to CSS), JSON models. No JS transpile; runtime JS ships as authored. Runtime dependency: `@sentry/browser` only. Local builds: `npm run build:json` and `npm run build:css`.
- **Is NOT:** no Java, Maven, OSGi, Sling, HTL, Dispatcher, Cloud Manager, `ui.apps`/`ui.content`, `.content.xml`, `pom.xml`, CRX packages, Content Fragments/GraphQL, QueryBuilder, or Servlets. **Never introduce these.** Sass is **dev-only** (see `docs/handbook/15-scss-compiler.md`); it is not served by the CDN.

## Two block families
- **Shared/boilerplate blocks:** `cards`, `cards-*`, `columns`, `columns-feature`, `hero`, `carousel-*`, `header`, `footer`, `fragment`, forms, etc.
- **Dedicated `k811-*` blocks:** the migration components (`k811-hero`, `k811-story`, `k811-pillars`, `k811-team`, `k811-offers`, `k811-steps`, …), driven by the shared runtime `scripts/k811/k811-common.js` and the scoped design guide `styles/kotak811.css` (Manrope + IntersectionObserver scroll-reveal).

## Glossary (EDS terms an LLM must know)
- **Block:** the component unit — `blocks/{name}/{name}.js|.css|_{name}.json`.
- **`decorate(block)`:** the block's default-exported function that transforms delivered DOM (the "Sling Model + HTL" equivalent).
- **Section:** a group of blocks/default content between horizontal rules; carries `.section` and section classes.
- **Field-collapsing:** Universal Editor merges link+text field pairs, so a block's rendered **cell count varies** — always classify cells by content, never by index.
- **Three-phase loading:** eager (LCP only) → lazy (rest + header/footer + `lazy-styles.css`) → delayed (martech).
- **AEM Code Sync:** GitHub App that publishes pushed code to preview/live — the "deploy".
- **`createOptimizedPicture`:** `aem.js` helper producing responsive WebP `<picture>`.
- **`moveInstrumentation`:** preserves Universal Editor editing overlays when relocating nodes.
- **`.plain.html`:** the raw delivered block markup (inspect before coding).
- **xwalk:** the crosswalk authoring model — `_{block}.json` definitions/models/filters merged into the aggregates.

## FAQ
- **"Where does component logic go?"** → `blocks/{name}/{name}.js`, in `decorate(block)`.
- **"How do I add an author field?"** → edit `_{block}.json`, then `npm run build:json`.
- **"How do I query content?"** → `query-index.json` (config in `helix-query.yaml`), fetched + filtered in JS. No GraphQL/QueryBuilder.
- **"How do I deploy?"** → push the branch; AEM Code Sync publishes. No manual deploy, no Cloud Manager.
- **"How do I invalidate cache?"** → re-publish (push). No Dispatcher/TTL.
- **"Where's the build?"** → no JS transpile. `npm run build:json` for UE aggregates; `npm run build:css` for optional block SCSS → CSS (`docs/handbook/15-scss-compiler.md`).
- **"Can I add a library?"** → only with justification; every KB ships to the browser. Prefer the ~2KB shared IntersectionObserver over animation libs.

## Why these facts are captured here
An LLM answering repository questions needs a single, dense, verified fact sheet so it doesn't hallucinate a traditional-AEM answer (the most common failure mode for an AEM-trained model on an EDS repo). The glossary exists because EDS vocabulary (block, decorate, field-collapsing, Code Sync) differs fundamentally from AEMaaCS vocabulary, and mixing them produces wrong guidance. The FAQ pre-answers the exact questions where a model is most likely to reach for the wrong (Java/Dispatcher/GraphQL) tool.
